## Задание 1 — золотой набор 30–40 пар → `tests/gold-set.jsonl`

**Что нужно:** расширить 20 пар из Lab 3 до 30–40: **5–7 «сложных»** (нужен синтез из нескольких чанков), **3–5 «негативных»** (вне корпуса, система должна отказаться).

**Предложение:**
- Не менять `tests/eval-set.jsonl` (на нём держатся тесты и отчёты Lab 3–4). `gold-set.jsonl` — надмножество: 20 старых + новые.
- Поля: `id`, `type` (`simple` / `multi_chunk` / `negative`), `query`, `relevant_chunk_ids` (список; у `simple` — один), `expected_answer` (1–3 предложения эталона **своими словами** на основе статей), `key_points` (2–4 коротких факта, которые обязаны быть в ответе), `should_refuse` (bool), `paraphrases` (1–2 перефразировки для задания 4), `evidence` (цитата из чанка — как в Lab 3).
- Итого: 20 simple + ~7 multi_chunk + ~5 negative = 32; при желании добавить ещё несколько simple до 35.
- **Сложные** (примеры; уточним по корпусу): «Какие обязанности у deployer высокорисковой системы и когда нужна оценка воздействия на права?» (ст. 26 + 27); «Чем отличаются обязанности провайдера GPAI и GPAI с системным риском?» (ст. 53 + 55); «Если система распознаёт эмоции на работе, это запрещено или высокий риск?» (ст. 5 + annex III); штраф за запрещённую практику vs за нарушение прозрачности (ст. 99 части).
- **Негативные**: 3 явно вне темы (рецепт, погода, курс акций) + 2 «пограничных» из соседней области, которых нет в корпусе (GDPR: «Какой штраф по GDPR за утечку данных?»; AI-законодательство США/Китая). Пограничные — самые интересные: модель может ответить из собственных знаний.
- `tests/test_gold_set.py`: как `test_eval_set.py` — уникальность, диапазон 30–40, все `relevant_chunk_ids` существуют, `evidence` реально встречается в тексте, у negative нет chunk_id.

**Готово:** набор сохранён, тест валидности зелёный.

## Задание 2 — оценочный скрипт `src/rag/evaluate.py`

**Метрики (по условию):**
1. **Recall@5 ретривера** (hybrid + binding-only) на simple и multi_chunk. Для multi_chunk считаем две версии: *any* (найден хотя бы один нужный чанк) и *all* (все) — «all» показывает реальную проблему синтеза.
2. **Доля ответов с валидными цитатами**: среди запросов, где модель ответила (`status = ok`), у скольких контракт выполнен. Честно разделить: *с первой попытки*, *после retry*, *`uncertain`*. Учесть, что «валидно» — формальная проверка, а не смысловая.
3. **Доля корректных отказов на негативных**: корректный отказ = `status = insufficient_context`. `uncertain` (контракт нарушен дважды) считаем отдельно, не как удачный отказ.

**Дополнительно (дёшево, но важно для вывода):** доля *ложных отказов* на позитивных запросах; доля ответов, где `key_points` присутствуют (проверка по ключевым словам, без LLM-судьи); время ответа.

**Реализация:** цикл по gold-set → `answer()` → запись всех сырых результатов в `reports/lab-5/runs.json` → агрегаты в `metrics.json` и таблицу в консоль. Флаг `--cached` пересчитывает метрики без вызова LLM.

## Задание 4 — 2–3 метаморфных теста (`tests/test_metamorphic.py` + раздел в `evaluate.py`)

Метаморфное отношение: **перефразирование не меняет смысл, значит выдача должна быть близкой**.
- **MR1:** Recall@5 на оригиналах vs на перефразировках; допустимое падение — порог (например ≤ 0,10) фиксируем *после* измерения и честно пишем, что порог выбран по данным. Только ретривер, детерминированно, без LLM.
- **MR2:** Jaccard множеств top-5 `chunk_id` для пар (оригинал, перефраз.). Ретривер, без LLM.
- **MR3:** Jaccard множеств **цитируемых** чанков для тех же пар. Нужен LLM → ~2× запросов.

В отчёт: наблюдаемый уровень инвариантности (средний Jaccard, доля пар с идентичным top-1, пары с наибольшим расхождением и почему). Перефразировки писать вручную и проверять на сохранение смысла (иначе тест мерит не систему, а плохую перефразировку).

## Риски
1. **Лимиты Groq.** ~35 запросов + перефразировки + retry + пробы — сотни обращений по ~2–4k токенов. Free-tier может не вытянуть 70B за день. Митигации: кэш, прогон MR1–MR2 без LLM, при необходимости `GROQ_MODEL=llama-3.1-8b-instant` для массовых прогонов (но тогда в отчёте указать, какая модель дала цифры).
2. **Недетерминизм.** `temperature=0` не гарантирует идентичных ответов у облачной модели; кэш фиксирует конкретный прогон, это нужно оговорить.
3. **Эталон «expected_answer» субъективен.** Проверяем `key_points` по ключевым словам — грубо; не выдавать это за измерение корректности.
4. **Мала выборка:** 1 запрос = 2,5–3 п.п.; различия в 1–2 запроса — не доказательство.
5. **Утечка из набора:** параметры (k, режим, промпт) уже подбирались по eval-set; gold-set включает те же 20 запросов, поэтому на них метрики оптимистичны. Новые 10–15 запросов дают более честную оценку — считать метрики отдельно «старые 20» / «новые».
