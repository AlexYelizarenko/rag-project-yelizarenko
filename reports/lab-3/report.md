# Лабораторна робота 3 — Векторні ембедінги та пошуковий індекс

## 1. Оцінювальний набір

**Файл:** `tests/eval-set.jsonl` — 20 пар «запит — релевантний чанк», по одному JSON-об'єкту на рядок.

### 1.1. Формат запису

```json
{"id": "q04", "query": "Do companies have to train their staff who work with AI?", "relevant_chunk_id": "article_4", "citation": "Article 4", "topic": "AI literacy", "evidence": "sufficient level of AI literacy"}
```

| Поле | Призначення |
| --- | --- |
| `id` | Ідентифікатор запиту (`q01`–`q20`) |
| `query` | Питання так, як його поставив би не-юрист |
| `relevant_chunk_id` | `chunk_id` еталонного чанка з `chunks.jsonl` — саме його рахує Recall@k |
| `citation` | Стаття/пункт для людини (напр. `Article 99(3)`) |
| `topic` | Тема; у наборі всі 20 тем різні |
| `evidence` | Коротка цитата з еталонного чанка, яка доводить, що чанк містить відповідь |

### 1.2. Як формувався набір

1. Обрано 20 тем, що покривають основні частини регламенту: визначення та ролі, сферу дії, заборонені практики, класифікацію та вимоги до систем високого ризику, обов'язки впроваджувачів, прозорість, моделі загального призначення (GPAI), підтримку інновацій, нагляд після виведення на ринок, права осіб, штрафи, дати застосування.
2. Для кожної теми сформульовано питання простою мовою, без дослівного копіювання тексту закону — щоб перевіряти семантичний пошук, а не збіг слів.
3. Еталонний чанк обрано вручну за вмістом корпусу: це чанк, у тексті якого безпосередньо міститься відповідь. Для питань про обов'язки обиралися статті/додатки (обов'язкові норми); один запит (q20) навмисно має еталоном преамбулу (recital 102), бо питання стосується мети правила, а не самого обов'язку.
4. Для кожної пари збережено `evidence`. Тест `tests/test_eval_set.py` перевіряє: розмір 15–25; унікальність `id`, запитів, еталонних чанків і тем; що кожен `relevant_chunk_id` існує в `chunks.jsonl`; що `evidence` дійсно є в тексті еталонного чанка (з нормалізацією переносів рядків PDF).

Мова запитів — англійська, як і мова корпусу (текст Official Journal), щоб модель ембедінгів не мала додаткової різниці мов. Українські запити можна перевірити окремим експериментом пізніше.

### 1.4. Обмеження та спостереження

- **Один еталон на запит.** Через структурне розбиття відповідь інколи є і в сусідньому чанку тієї ж статті (наприклад, `article_5_part_2`). Для Recall@k такий результат рахується як промах; це буде враховано під час аналізу в завданні 5.
- **Довжина чанків.** Для частини еталонів відповідь стоїть далеко від початку чанка (q14 — з 239-го токена, q18 — з 210-го). all-MiniLM-L6-v2 обрізає вхід до 256 токенів; перевірка в розділі 2.4 показала, що в усіх 20 еталонах фраза-доказ потрапляє в межі цього ліміту. `article_5_part_1` має 4 790 символів (947 токенів), тому запит q05 сформульовано загально (заборонені практики в цілому), а не про конкретний пункт.
- **Артефакт PDF.** У статті 51 поріг «10^25 FLOP» у витягнутому тексті має вигляд «1025» (верхній індекс втрачено). Тому `evidence` для q13 — фраза без числа. Виправлення екстракції верхніх індексів — можливе покращення пайплайна лабораторної 2.

## 2. Модель ембедінгів

**Модуль:** `src/retrieval/embeddings.py`. **Запуск:** `uv run python -m retrieval.embeddings`.

### 2.1. Обрана модель і обґрунтування

**`sentence-transformers/all-MiniLM-L6-v2`** — 6-шарова модель (≈22,7 млн параметрів), вектор розмірністю 384, максимальна довжина входу 256 токенів.

- **Рекомендована умовою роботи** і є стандартною базовою моделлю для семантичного пошуку англійською мовою; навчена на понад 1 млрд пар «запит — текст», тобто саме на задачі, близькій до нашої (питання користувача → фрагмент закону).
- **Компактна:** ≈90 МБ, працює на CPU. Кодування всього корпусу (540 чанків) займає ≈16 с на ноутбуці з Intel CPU, тому ембедінги можна швидко перераховувати під час експериментів.
- **Мова відповідає корпусу:** текст регламенту і запити оцінювального набору — англійською.
- **Розмір корпусу малий** (540 чанків), тому більша модель не дає переваги в швидкості чи пам'яті, а лише ускладнює запуск.

Розглянуті альтернативи:

| Модель | Розмірність | Ліміт входу | Чому не обрана зараз |
| --- | --- | --- | --- |
| `all-mpnet-base-v2` | 768 | 384 токени | Якісніша, але в ≈5 разів повільніша; має сенс лише якщо recall MiniLM буде низьким |
| `BAAI/bge-small-en-v1.5` | 384 | 512 токенів | Довший вхід менше обрізає чанки; кандидат для порівняння в завданні 5 |
| `paraphrase-multilingual-MiniLM-L12-v2` | 384 | 128 токенів | Підтримує українські запити, але ще коротший ліміт входу |

### 2.2. Середовище

Ноутбук з Intel macOS накладає обмеження: остання збірка PyTorch для цієї платформи — 2.2.2, тому проєкт переведено на Python 3.12 і зафіксовано сумісні версії: `torch==2.2.2`, `transformers==4.57.6` (5.x потребує torch ≥ 2.6), `sentence-transformers==5.7.0`, `numpy==1.26.4` (torch 2.2.2 зібраний під NumPy 1.x). Версії закріплено в `pyproject.toml` і `requirements.txt`.

### 2.3. Процес

1. Читаємо `reports/lab-2/chunks.jsonl` (корпус лабораторної 2 без змін).
2. Кодуємо `page_content` кожного чанка (батчі по 32, CPU). Текст включає заголовок `Article N – Title`, тому вектор кожної частини статті містить і її тему.
3. Вектори нормалізуємо до одиничної довжини: тоді косинусна подібність дорівнює скалярному добутку. Запити кодуються тією ж функцією `embed_texts`.
4. Зберігаємо в `data/embeddings/` (не в git, відтворюється однією командою): `vectors.npy` — матриця 540 × 384 (float32, 830 КБ); `chunk_ids.json` — `chunk_id` у тому ж порядку (рядок `i` матриці ↔ `chunk_ids[i]`); `summary.json` — статистика нижче.

### 2.4. Результат

| Показник | Значення |
| --- | --- |
| Кількість векторів | 540 (усі чанки корпусу) |
| Розмірність | 384, float32, нормалізовані |
| Час завантаження моделі / кодування | ≈3 с / ≈16 с (CPU) |
| Довжина чанків у токенах (мін / медіана / середнє / макс) | 25 / 222 / 213 / 947 |
| Чанків, довших за ліміт 254 токени (обрізаються) | 215 з 540 (40 %): 117 статей, 77 преамбули, 21 додатки |

Тести `tests/test_embeddings.py` перевіряють: розмірність 384 і нормалізацію; що запит про заборони ближчий до тексту про заборонені практики, ніж до нерелевантного речення; що збережені вектори відповідають корпусу (кількість і порядок `chunk_id`).

**Обрізання входу.** Модель бачить лише перші 254 токени чанка (+2 службові), тобто для 40 % чанків кінець тексту не впливає на вектор. Для оцінювального набору це перевірено окремо: в усіх 20 еталонних чанках фраза-доказ починається до 254-го токена (найпізніше — q14, токен 239), тож обрізання не приховує відповіді в еталонах. Для загального пошуку це обмеження лишається; його вплив можна виміряти в завданні 5 порівнянням з моделлю з довшим входом (`bge-small-en-v1.5`, 512 токенів), не змінюючи корпус.

## 3. Векторний індекс

**Модуль:** `src/retrieval/index.py`. **Запуск:** `uv run python -m retrieval.index`.

Обрано **Chroma** (локальний persistent client) — так було заплановано ще в лабораторній 1; для 540 векторів серверний Qdrant / FAISS не потрібні.

### 3.1. Процес

1. Читаємо `reports/lab-2/chunks.jsonl`.
2. Беремо готові вектори з `data/embeddings/vectors.npy` (якщо порядок `chunk_id` збігається); інакше кодуємо заново тією ж моделлю.
3. Створюємо колекцію `eu_ai_act` з `hnsw:space = cosine`.
4. Для кожного чанка зберігаємо: текст (`page_content`), вектор, метадані Lab 2 (`chunk_id`, `chunk_index`, `source_doc_id`, `section_type`, `binding`, сторінки, поля статті/додатка тощо). Chroma приймає лише скаляри `str` / `int` / `float` / `bool` — у корпусі інших типів немає.
5. Індекс пишеться в `data/index/chroma/` (git-ignored). Відтворення — однією командою вище; `summary.json` у цій теці дублює статистику.

### 3.2. Статистика індексу

| Показник | Значення |
| --- | --- |
| Кількість векторів | 540 |
| Розмірність | 384 |
| Метрика | cosine (score у CLI = `1 − distance`) |
| Шлях | `data/index/chroma/` |
| Розмір на диску | ≈ 8,0 МБ (`disk_bytes` ≈ 8 360 100) |

Тести `tests/test_retrieval_index.py` перевіряють: 540 записів; метадані зразка `article_3_def_4`; що CLI-пошук повертає top-k зі спадними score.

## 4. Пошук через CLI

**Модуль:** `src/retrieval/search.py`.

```bash
uv run python -m retrieval.search "What is a deployer under the AI Act?"
uv run python -m retrieval.search "..." --k 5 --binding-only
```

Запит кодується тією ж `embed_texts` (нормалізовані вектори). Результат: top-5 з `chunk_id`, cosine similarity, сторінками PDF і коротким прев’ю. Повні приклади збережено в `reports/lab-3/cli-examples.md`.

### 4.1. Приклади (скорочено)

**Запит:** `What is a deployer under the AI Act?` — еталон `article_3_def_4` на **1-му** місці (score ≈ 0,75).

**Запит:** `Must a human be able to supervise a high-risk AI system?` — еталон `article_14_part_1` у top-5.

**Запит:** `Which uses of AI are completely banned in the EU?` — без фільтра top-5 засмічують преамбули / технічні статті; еталон `article_5_part_1` поза top-5. Це узгоджується з низьким Recall для q05 і мотивує експеримент `binding_only` у розділі 5.

**Запит:** `From which date do the bans on prohibited AI practices apply?` — верх повертає recital 179 (`intro_232`), який прямо каже, що заборони мають застосовуватися з 2 лютого 2025 — тобто відповідь фактично правильна, але еталон — стаття 113, тому для строгого Recall@k це промах. Стаття 113 не містить слів про заборони (лише «Chapters I and II shall apply from 2 February 2025»).

Score у виводі — **косинусна подібність** (`1 −` відстань Chroma в просторі cosine), діапазон приблизно 0…1; більший score = ближче.

## 5. Recall@5 / Recall@10 і підбір параметрів

**Модуль:** `src/retrieval/evaluate.py`. **Запуск:** `uv run python -m retrieval.evaluate`.  
Детальний JSON: `reports/lab-3/recall.json`.

Метрика: частка запитів, для яких **точний** `relevant_chunk_id` потрапляє в top-k. Сусідня частина тієї ж статті рахується як промах.

### 5.1. Експерименти

| Налаштування | Опис | Recall@5 | Recall@10 |
| --- | --- | ---: | ---: |
| `raw_query` | запит як є | 0,50 | 0,75 |
| `eu_ai_act_prefix` | префікс `EU AI Act: ` | 0,30 | 0,45 |
| `regulation_prefix` | префікс `Regulation (EU) 2024/1689: ` | 0,15 | 0,25 |
| **`binding_only`** | фільтр `binding=true` (без преамбул) | **0,65** | **0,80** |

### 5.2. Висновок щодо параметрів

**Найкраще налаштування: `binding_only`** (пошук лише серед обов’язкових норм).

- Префікси до запиту **погіршують** recall: вони зсувають вектор запиту і не допомагають MiniLM на цьому корпусі.
- Фільтр `binding=true` прибирає преамбули, які часто опиняються вище статей (як у CLI-прикладі про заборони). Recall@5 зростає з 0,50 до 0,65, Recall@10 — з 0,75 до 0,80.
- Очікувана ціна: q20 (еталон — recital 102) стає промахом, бо преамбули відфільтровані. Для питань про обов’язки це прийнятний компроміс; для питань «чому так написано в преамбулі» фільтр треба вимикати (`raw_query`).

CLI за замовчуванням лишає повний корпус; рекомендований режим для обов’язків: `--binding-only`.

### 5.3. Промахи (найкраще налаштування)

Поза top-10 при `binding_only`: q05 (заборони), q10 (обов’язки впроваджувачів), q19 (дата застосування Art. 113), q20 (open-source recital — очікувано).

Типові причини: запит збігається за змістом з пояснювальним мотивом, а не зі статтею (q19: мотив 179 фактично містить правильну дату, але еталон — стаття 113); дуже довгий чанк Art. 5 (947 токенів, модель бачить лише початок; причину не доведено експериментально) (q05); сусідні статті/визначення та статті 104–109 про зміни інших регламентів ранжуються вище точного еталона.
